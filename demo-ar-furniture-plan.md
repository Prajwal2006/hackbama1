# AR Furniture Demo: Step-by-Step Build Plan

**Demo in one sentence:** A judge opens a link on their phone, taps a piece of furniture (desk, mirror, table lamp), grants camera permission, and sees a true-to-size 3D model placed in their real room through AR.

**Scope for the hackathon demo:**
- A mobile-friendly web app with a small catalog of 3-4 items.
- 3D models are generated by the agent (procedural stand-ins), not scanned. The scanning pipeline from Phase 1 remains the product vision; the demo proves the *buyer experience*.
- Served from a laptop on the local network so judges can open a link like `https://192.168.1.10:3000`.

---

## 0. Read this first: three constraints that decide the design

These are the most likely things to break the demo. Check them early.

### Constraint 1: Camera and AR need HTTPS, not plain `http://`
Browsers only allow camera access and WebXR on **secure contexts**: `https://` or `localhost`. A plain `http://192.168.1.10:3000` link will **not** get a camera prompt on a judge's phone.

**Fix:** serve the app over HTTPS.
- **Option A (recommended for the demo):** self-signed HTTPS on the laptop (Vite's `basic-ssl` plugin or `mkcert`). The judge sees a one-time "connection not private" warning and taps *Advanced > Proceed*.
- **Option B (backup):** a free tunnel such as Cloudflare Tunnel or ngrok. This gives a real `https://` link with no warning, and works even if venue Wi-Fi blocks device-to-device traffic. It needs internet.

### Constraint 2: Android and iPhone do AR differently
| Platform | How AR works | Needs |
|---|---|---|
| Android (Chrome) | WebXR or Google Scene Viewer, with real surface tracking | ARCore-supported phone |
| iPhone (Safari) | **AR Quick Look** (Apple's viewer). Safari does not support WebXR | A USDZ file. The `<model-viewer>` library can generate one from the GLB automatically |

Using Google's `<model-viewer>` web component covers both platforms with one codebase. Note: on iPhone, AR opens Apple's viewer (a full-screen handoff), not an in-page camera view. That's normal and still impressive.

### Constraint 3: Venue Wi-Fi may block phone-to-laptop traffic
Many hackathon/campus networks use "client isolation". If judges' phones can't reach the laptop, use your **own phone's hotspot** or a **small travel router** and put judges on it, or fall back to the tunnel (Option B above).

## Tech stack (kept deliberately simple)

| Piece | Choice | Why |
|---|---|---|
| App | Vite + plain JavaScript (or React if the team prefers) | Fast, tiny, easy for the agent to generate |
| AR + 3D viewing | `@google/model-viewer` | Handles Android WebXR/Scene Viewer and iOS Quick Look |
| 3D models | GLB files generated by a Three.js script | Agent-authorable, no art skills needed |
| HTTPS | `@vitejs/plugin-basic-ssl` | One config line |
| Hosting | Laptop dev server on port 3000, bound to all interfaces | Matches your `http://192.168.1.10:3000` idea (but with https) |

## Roles

- **Agent:** writes code and generates the models.
- **Human verifier:** runs each checkpoint, ticks the box, and only then moves on.
- **Test devices needed:** at least **one Android phone** and **one iPhone**, plus the laptop. Note each model/OS version in Step 8.

---

## Step 1: Project setup and server reachable from a phone
**Goal:** An empty "Hello" page that a phone can open over the network.

**Agent tasks**
1. Create a Vite project.
2. Configure the dev server: `host: true` (listen on all interfaces), `port: 3000`, and the `basic-ssl` plugin for HTTPS.
3. Add a `README` with the run command.

**Human tasks**
1. Connect laptop and phone to the **same** Wi-Fi (or the hotspot).
2. Find the laptop's IP (`ipconfig` on Windows, `ifconfig`/System Settings on Mac).
3. Allow the app through the laptop firewall if prompted.

**Verify**
- [ ] `npm run dev` starts without errors.
- [ ] Laptop browser opens `https://localhost:3000` and shows the page.
- [ ] Phone opens `https://<laptop-ip>:3000`, accepts the certificate warning, and sees the same page.
- [ ] Repeat on both Android and iPhone.

**If it fails:** wrong IP, firewall, or client isolation. Try the phone hotspot. Still failing, set up the tunnel (Option B) now.

---

## Step 2: Generate the first 3D model (the desk)
**Goal:** One valid, realistically sized `desk.glb` file.

**Agent tasks**
1. Write a Node/Three.js script (`scripts/generate-models.js`) that builds the desk from simple shapes (box tabletop, four box or cylinder legs, optional drawer block).
2. Build it in **real-world meters** so the size is correct in AR (for example 1.2 m wide x 0.6 m deep x 0.75 m tall).
3. Give it sensible materials: wood-colored top, darker legs.
4. Export to `public/models/desk.glb` using `GLTFExporter`. (If Node export is troublesome, the fallback is a small browser page with a "Download GLB" button.)

**Verify**
- [ ] `desk.glb` exists and is under about 1 MB.
- [ ] Drag the file into an online glTF viewer (for example gltf-viewer.donmccurdy.com). It loads with no errors.
- [ ] The viewer reports roughly the intended dimensions.
- [ ] It looks like a desk (legs touching the floor, nothing floating).

---

## Step 3: Show the model in the browser (no AR yet)
**Goal:** A page where the desk can be rotated and zoomed.

**Agent tasks**
1. Add `<model-viewer>` pointing at `desk.glb` with `camera-controls`, good lighting (`environment-image="neutral"`, `shadow-intensity`), and a neutral background.

**Verify**
- [ ] Desk renders on laptop.
- [ ] Desk renders on both phones, and can be rotated by touch and pinch-zoomed.
- [ ] Load time is a couple of seconds or less on Wi-Fi.

---

## Step 4: Turn on AR
**Goal:** "View in your room" works on phones.

**Agent tasks**
1. Add the `ar` attribute with `ar-modes="webxr scene-viewer quick-look"`.
2. Set `ar-scale="fixed"` so the model appears at real size (not user-resizable).
3. Add `ar-placement="floor"` for floor items (desk, table).
4. Add a clear custom "View in your room" button.

**Human tasks:** On the phone, tap the button and grant camera permission when asked.

**Verify**
- [ ] **Android:** camera permission prompt appears, you can scan the floor, the desk is placed on it, and you can walk around it.
- [ ] **iPhone:** Quick Look opens, the desk is placed, you can move/rotate it.
- [ ] **Size check:** a real tape measure shows the virtual desk matches the stated size (within a few centimeters). Do this once; it's your best demo talking point.
- [ ] Button is hidden or shows a helpful message on unsupported devices (for example on a laptop).

**If it fails on Android:** confirm Google Play Services for AR (ARCore) is installed and the phone is on ARCore's supported list. Confirm you're on HTTPS.

---

## Step 5: Generate the rest of the catalog
**Goal:** Mirror, table lamp, and one more item (suggested: a chair or small side table), each a valid GLB.

**Agent tasks**
Extend the generator script, with real-world sizes:

| Item | Suggested shape | Approx. size (W x D x H) | AR placement |
|---|---|---|---|
| Desk | Box top + legs (done in Step 2) | 1.2 x 0.6 x 0.75 m | floor |
| Mirror | Thin box frame + flat reflective-looking panel, leaning/standing | 0.5 x 0.05 x 1.5 m | floor |
| Table lamp | Cylinder base, tapered shade, thin stem | 0.25 x 0.25 x 0.45 m | floor (a "table" is also fine) |
| Chair or side table (optional) | Box and cylinder primitives | about 0.45 x 0.45 x 0.9 m | floor |

Tips: keep each file small, give every model a flat base at y=0 so it sits on the floor, and give the lamp an emissive (glowing) shade for a nice demo effect.

**Verify (per model)**
- [ ] File loads in the glTF viewer with no errors.
- [ ] Recognizable as the item, with the base at floor level.
- [ ] Opens in AR on both phones at a believable size.

---

## Step 6: Build the catalog UI and product page
**Goal:** A phone-friendly storefront flow: browse, pick, view in AR.

**Agent tasks**
1. **Catalog screen:** 3-4 large cards (name, thumbnail, "view" action). Design for one-handed phone use.
2. **Product screen:** `<model-viewer>` for the selected item, name, a "View in your room" button, and a **dimensions panel** (W x D x H).
3. Store the catalog in a single `catalog.json` (id, name, model path, dimensions in cm, description). **Keep dimensions in this data file, separate from the mesh**, as in the Phase 1 plan.
4. Add a short on-screen hint: "Point your camera at the floor and move your phone slowly."
5. Add a friendly fallback message for unsupported browsers.

**Verify**
- [ ] Every card opens the right model.
- [ ] Dimensions shown match the physical size seen in AR.
- [ ] A non-technical teammate can complete the flow without instructions.
- [ ] Layout is readable on a small phone screen.

---

## Step 7: Polish for judges (only after Steps 1-6 pass)
**Goal:** Make the demo robust and self-explanatory.

**Agent tasks (pick what time allows)**
1. Add a **QR code** page or poster so judges can scan instead of typing the IP.
2. Add a short "How to try it" banner on the home screen (3 steps).
3. Preload models so AR opens fast.
4. Add a simple "Reserve this item" button that shows a confirmation screen (mock only), to connect the demo to the Furniture Bank idea.
5. Optional stretch: a simple "does it fit?" panel where the user enters room width/depth and the app compares it against item dimensions.

**Verify**
- [ ] QR code opens the app on a phone with no typing.
- [ ] Judges can finish the flow in under 60 seconds with no help.

---

## Step 8: Network rehearsal and device matrix
**Goal:** Prove it works under real demo conditions.

**Human tasks**
1. Do the full run at the venue (or on a similar network), with the laptop plugged into power.
2. Test with at least 2 phones not belonging to the team, one of each OS.
3. Record results:

| Device | OS / browser | Opens link | Camera prompt | AR works | Notes |
|---|---|---|---|---|---|
| | | | | | |

**Verify**
- [ ] Works on both OSes from a fresh phone (no prior certificate acceptance).
- [ ] Works with 3-5 phones connected at once.
- [ ] Laptop doesn't sleep, change IP, or lock during the test. Set a **static IP or DHCP reservation** if possible and disable sleep.
- [ ] Backup path tested: tunnel URL or hotspot.

---

## Step 9: Demo day checklist and fallbacks

**Before judges arrive**
- [ ] Laptop charged and plugged in, sleep disabled, dev server running.
- [ ] Link and QR code printed or displayed.
- [ ] Fresh IP confirmed (`https://<ip>:3000` opens on a phone).
- [ ] Backup tunnel URL ready in a note.
- [ ] A **screen recording** of the AR flow saved on a phone in case the network fails.

**Suggested 60-second pitch**
1. "Buying second-hand furniture is risky. Will it fit? Will it look right?"
2. Open the link, pick the desk, tap "View in your room", and show it at real size.
3. "Today these are generated models. In production, students scan their own furniture with LiDAR (Phase 1), so every listing is a true digital twin of the actual item."

**Be upfront with judges:** the demo models are generated stand-ins, and the scanning pipeline is the roadmap. Saying this clearly builds trust.

---

## Risk summary

| Risk | Likelihood | Mitigation |
|---|---|---|
| No camera prompt (HTTP instead of HTTPS) | High if ignored | HTTPS in Step 1, verified on a phone |
| Venue Wi-Fi blocks phones from the laptop | Medium | Hotspot / travel router / tunnel |
| Judge's phone doesn't support AR | Medium | 3D viewer still works; keep a team phone ready to demo AR |
| iPhone AR opens Quick Look instead of in-page | Certain | Expected behavior; explain it |
| Generated model looks crude | Medium | Add rounded edges, two-tone materials, soft shadows; keep shapes simple |
| Scale looks wrong in AR | Low-Medium | Build in meters, `ar-scale="fixed"`, tape-measure check in Step 4 |
